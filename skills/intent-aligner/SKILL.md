# 意图对齐器（Intent Aligner）

使用此技能确保 Codex 在动手前真正理解用户的意图。保持交互轻量：先对齐，解决少数几个价值最高的未知项，指出用户可能没关注到的盲点，然后停下。

在对齐阶段不要实现代码、编辑文件、运行实验或产出交付物,除非用户明确结束对齐并要求执行。

## 核心原则（所有模式通用）

1. **先查证,再提问。** 如果一个事实可以从仓库、文档、配置、历史消息或可见文件中查到,就自己去查,不要问用户。
2. **区分事实与猜测。** 陈述假设时,标注哪些是查证过的（已查证）,哪些是猜的（猜测）。用户应该一眼就能看出哪些假设是可靠的。
3. **优先质疑错误前提。** 如果请求建立在技术上错误或有风险的前提之上,先直接指出,再问细节问题。质疑前提的优先级高于打磨细节。
4. **每个问题都必须能改变下一步行动。** 如果答案不会影响你接下来做什么,就不要问。

## 第一步：判断对齐规模

数一数**独立决策点**——即不同的合理选择会导致明显不同结果的地方：

- **0–1 个决策点 → 快速对齐。** 适用于小任务、小改动、简单的实验调整、文字修改,或不清晰但范围有限的请求。
- **2 个及以上决策点 → 迭代对齐。** 适用于多个选择相互影响的中型任务,但完整的 Plan Mode、PRD 或架构设计又太重。

其他倾向迭代对齐的信号：改动跨多个文件/模块、难以回退、影响他人依赖的接口。

如果快速对齐后用户的回答暴露出任务比预想的大,直接说明并升级到迭代对齐。如果迭代对齐中发现任务需要真正的设计工作,建议转入 Plan Mode,不要硬撑着用这个技能。

## 快速对齐

用以下格式回复一次：

````text
我理解你要的是：
- ...

我现在默认假设：
- [已查证] ...
- [猜测] ...

我还不确定（括号内是我的默认处理，回复"按默认"即可）：
1. ...（默认：...）
2. ...（默认：...）
3. ...（默认：...）

你可能没关注到的点：
- ...
````

规则：

- 最多问 3 个不确定项,每个问题必须附带推荐的默认处理。
- 如果没有有意义的未知项,省略"我还不确定"部分。
- 如果没有达标的盲点（见下方"盲点检查"）,省略盲点部分,绝不硬凑。
- 问具体的、可直接回答的问题,不要问"你怎么看?"这类宽泛问题。
- 用户回答后（或说"按默认"/"就按你理解的来"）,输出对齐结论（见下方）并停止,除非用户要求执行。

## 迭代对齐

最多进行 5 轮对齐。一旦下一步行动足够清晰就提前结束。

每轮必须：

1. 用 2–5 个要点复述当前理解。
2. 指出相比上一轮,哪些点发生了变化或变清晰了。
3. 只问 1 个杠杆最大的问题,并在有用时附带推荐的默认答案。
4. 如有需要,随问题附带最多 1 个盲点提示。

使用以下格式：

````text
当前理解：
- ...

已确认/更新：
- ...

（可选）你可能没关注到的点：...

我建议默认按 ... 处理。

唯一还需要你定的是：...
````

如果 5 轮之后仍未对齐,不要继续循环：用一条消息总结剩余的分歧点,请用户拍板,或建议转入 Plan Mode。

## 对齐结论（两种模式通用）

对齐完成后,始终输出：

````text
对齐结论：
- 目标：...
- 不做什么：...
- 默认执行策略：...
- 已接受的风险/盲点：...（如无则省略）
````

然后停止。除非用户明确要求,不要继续进入实现。这个结论是后续执行的锚点——尤其是"不做什么"这一条,用来防止范围蔓延（scope creep）。

## 盲点检查

回复前,扫描用户可能没有考虑到的细节。检查以下类别：

- **边界情况与失败模式**：空输入、并发、部分失败、边界值。
- **隐藏状态与数据假设**：违反新逻辑的存量数据、数据迁移、缓存/过期状态。
- **下游影响**：调用方、使用方、CI,以及依赖当前行为的其他模块或人。
- **不可逆性与成本**：难以撤销的改动、长时间运行的任务、配额/费用、破坏性操作。
- **成功标准**：用户如何判断做成了——请求里没提到的指标、测试或评估方式。
- **更简单的替代方案**：已有的工具、参数或库,可能让这个需求根本不用做。

准入门槛——一个盲点必须**同时满足三条**：

1. 用户没有表现出考虑过它的迹象。
2. 如果忽略,可能改变结果或导致返工。
3. 现在就可以对它做出决策（在对齐阶段可处理）。

快速对齐最多列 2 个盲点,迭代对齐每轮最多 1 个。零个是完全正常的数字——不要为了显得周全而编造顾虑。泛泛的建议（"注意代码质量"、没有具体理由的"记得写测试"）永远不达标。

## 提问纪律

- 迭代对齐中一次只问一个问题。
- 只有当选项是真实的权衡取舍时,才用选择题形式。
- 不要为了礼貌而问凑数的问题。
- 不要把一个小请求变成完整的需求评审流程。
- 当假设会影响结果时,明确说出假设。
- 如果用户说"就按你理解的来"或"按默认",采用已声明的默认处理,输出对齐结论,结束对齐。
