# Prompt：技术与算法文献线

## 目标

从用户的数据形态、计算任务和设计挑战出发，找出研究必须对话的 **2–4 条技术文献流**：已有方法怎样做、在哪些条件下不足、用户的设计可能处于什么位置。技术线由挑战决定，不按模型名罗列。

## 输入

- 输入、输出、分析单位、监督信号、预测／决策时点和部署时可用信息。
- 文本、图、序列、多模态、层级、稀疏、选择性标签或非平稳等数据结构。
- 问题／视角文献图，以及用户当前方法与最不确定的技术贡献。
- 可选：候选论文全文，重点是 Introduction、Related Work、挑战、方法概览和贡献段。

## A. 检索前：从挑战生成技术流

1. 写出计算任务：`用[输入]，在[时点]，对[单位]预测／生成／选择[输出]。`
2. 把数据事实改写为 2–4 个设计挑战，例如“关系有方向且跨期”，而不是“想用 GNN”。
3. 对每个挑战给出：
   - 直接最近邻：解决相同任务与挑战的方法；
   - 技术祖先：提供关键表示、学习目标或约束的通用方法；
   - 简单对照：更常见或更便宜的替代方案；
   - 2–4 组查询式，采用“任务／数据结构 + 挑战 + 方法机制”的组合。
4. 说明该技术流为何与问题线相连；只有模型名称相同但任务、信息边界或贡献比较面不同的论文降为弱相关。

## B. 取得全文后：校准每篇论文

用表格提取：

`数据／任务挑战 → 既有技术流 → 典型做法 → 当前缺口 → 本文设计回应`

并为每项判断标注：

- **作者明示：** 作者直接批评、比较或声称的缺口；
- **阅读者归纳：** 从任务和机制推导的合理限制，但不是作者原话；
- **关系类型：** 最近邻、技术祖先、借用组件、简单对照或评估基线。

最后回写新的查询词、缺失的技术最近邻，以及哪些设计只是已有组件的新组合。

## 判断规则

- “性能不够”不是完整缺口；写清表示能力、监督、动态性、耦合、解释、信息可得性或部署限制。
- 作者没有系统回顾某技术时，不替作者补造文献流；把它列为下一轮需要检索的空白。
- 预测增益不自动证明理论机制；attention、学习图和潜在表示默认是模型内代理。
- 重要判断附 PDF 页码、章节或表图；结果表不是识别技术对话的主要依据。
