先理解文档角色

Skill 如何把研究规则变成项目实际文档

Skill 负责总路由，Prompt 负责当前步骤，Rules 负责约束，Template 负责输出骨架；AI 最终在具体科研项目中生成并维护真实文档。

例如：Dataset Profile 模板
项目真实状态与证据

实际生成文档

DATASET_PROFILE.md、RESEARCH_BRIEF.md、BENCHMARK.md、实验日志与 Stage Summary。

渐进式读取：SKILL.md 与唯一的 ALWAYS 契约组成常驻上下文；每轮只激活一个 PHASE，模板、日志与详细字段规范保持 ON_DEMAND。

CONTEXT.md：记录我们如何开发和裁决这套 Skill，不是实验运行时生成的科研文档。

Workflow HTML：帮助人和 AI 理解文件关系与生命周期，只负责可视化导航，不制定研究规则。

1 · 启动对齐

这是人工参与最多、也是唯一必须人工确认的阶段。AI 先查证，再提问。

输入

  • 数据集文件与项目代码
  • 用户完整需求与性能目标
  • 研究预算与允许的执行边界

执行顺序

  1. 检查可运行代码，无代码时安全引入 ReproFlow
  2. 生成并 validate Codebase Profile
  3. 读取数据并生成 Dataset Profile
  4. 自动填写可推断字段
  5. 围绕 PENDING 字段询问 3–5 个问题
  6. 生成 Research Brief 草案

使用文件

  • bootstrap_codebase.pyOperational
  • reproflow_code_contract.mdOperational
  • research_bootstrap.mdOperational
  • codebase_profile.mdOperational
  • dataset_profile.mdOperational
  • research_brief.mdOperational

离开条件

代码底座已建立或完成现有代码映射，Research Brief 字段完整并获得用户最终确认。确认后不再逐实验请求批准。

2 · 研究规划

把冻结目标变成不可漂移的评测契约和可渐进披露的研究 Roadmap。

必须冻结

  • 一个 Primary Metric 与 Performance Target
  • 零到多个 Hard Constraints
  • 数据划分、评估脚本与停止协议
  • 至少一个带单位的预算：wall_clock_hours / gpu_hours / monetary_cost + currency / formal_experiment_count
  • Anchor Baseline 或 Baseline Pending 状态

使用文件

  • benchmark_and_model_roles.mdOperational
  • research_records_protocol.mdOperational
  • benchmark_contract.mdOperational
  • master_roadmap.mdOperational

输出

BENCHMARK.md 与项目根目录的 EXPERIMENT_LOG.md。

3 · 文献与候选

不是只在开头调研一次，而是在复现、修复和后续组件创新中持续返回文献。

主要动作

  • 默认选择、下载并核验 3–4 篇近邻论文；Brief 冻结后无需再次确认数量
  • 恢复真正的算法机制
  • 选择全方法或组件级 R/A 复现
  • 必要时进行最多三个核心 Paper Repair 假设
  • 对 N candidate 执行伪创新与结构风险审查

使用文件

  • paper reproduction moduleOperational
  • candidate_priority_rules.mdOperational
  • interaction_review_gate.mdOperational
  • paper_mechanism_review.mdOperational
  • candidate_adversarial_review.mdSkeleton

输出

文献综述、逐篇 Paper Mechanism Card，以及通过硬门的 R/A/N 实验候选。

4 · 实验迭代

实验执行完全无人值守，但所有 Candidate 都必须可证伪、可比较并可追溯。

强制循环

假设 → 预测与证伪条件 → 修改 → Smoke → Full Run → 判断 → 保留 / 回滚 / 修复

Runtime 边界

LLM 负责机制、假设、解释和路线；Graph 判断动作只进入 handoff，落库动作映射到 propose 或 start-run。Experiment ID、Attempt 与 Card 仅由 start-run 创建；inspect 返回机器 current_phase + last_trigger + active_run，作为恢复唯一入口。成功响应使用 accepted / revision / result，拒绝响应使用 error_code / violations / allowed_next_actions。正式运行先登记 resolved config、metrics JSON、manifest、trainer log 与 Brief 派生的 cost unit，Runtime 从真实 artifact 读取指标后才更新科研状态。LLM 不直接编辑 canonical JSON、Runtime State 或派生 HTML。

分类与门控

  • 五维 Experiment Classification
  • N candidate 的 Gold / Silver / Hold / Reject
  • Research Base 晋升：TWO_SEEDS / ONE_CONFIRM_SEED / SINGLE_RUN_JUSTIFIED
  • Branch Addition Gate
  • Simplification Campaign

日志分层

  • Experiment Card：Runtime Record 由 Runtime 独占并校验 hash；Research Notes 只允许 LLM 追加
  • Research Experiment Log：精简研究叙事
  • Run Event Log：JSONL 机器事件流
  • trainer 输出：只作为被引用 artifact

5 · 反思总结

Stage Summary 不是日志缩写，而是对冻结证据的第一性原理分析、对抗审查和下一路线裁决。

触发条件

  • 累计十个正式实验
  • Research Base 正式晋升
  • Benchmark 正式变更
  • 研究方向关闭或切换
  • Paper Repair Cycle 结束

固定六问

  1. 我们到底知道了什么？
  2. 这些结果为什么发生？
  3. 我们可能错在哪里？
  4. 留下了什么可迁移认识？
  5. 下一阶段有哪些可判别方向？
  6. 研究路线现在应当怎么走？

按需 Gate

只有出现跨分支组合时读取 Interaction Review Gate；Stage Reflection 不重复定义规则。

路线

DEEPEN / BROADEN / REPAIR / PIVOT / CONCLUDE，并保留一个带触发条件的备用路线。

6 · 终止与特殊暂停

研究层面严格只有两个最终终止状态；HUMAN_REVIEW_REQUIRED 只是临时暂停。

TARGET_REACHED

完整可比结果达到冻结的 Primary Metric 目标，并且全部 Hard Constraints 通过。

TARGET_NOT_REACHED

wall_clock_hours、gpu_hours、带币种 monetary_cost、formal_experiment_count 中任一已登记硬预算先耗尽，目标仍未达到。

HUMAN_REVIEW_REQUIRED

仅限数据或评测有效性根本失效、外部阻塞在一次 Recovery Cycle 后仍无法恢复，或用户主动要求暂停或修改冻结契约。纯人工等待不计入墙钟预算，但既有和持续产生的资源消耗仍计入。

两者都必须输出

  • 最终总结与预算消耗
  • 最佳合格模型与完整实验谱系
  • 最终指标、目标差距与可复现 artifact
