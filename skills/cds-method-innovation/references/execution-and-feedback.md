# 实施、验证与回到创新问题

在实验方案明确且用户委托包含实施/运行时使用；它是本 Skill 内部阶段，不需要额外的实验执行 Skill。只委托设计时交付方案并停止。预算、环境或数据缺失就说明具体缺口，不把准备工作写成运行结果。

## 从方案到代码

1. 读取选定候选、方案、baseline 配置及相关源码。保持已有划分、指标和选择规则；改变协议需记录原因和新版本。
2. 将机制差异落实为能定位的代码改动，保留原 baseline 的可运行路径。检查关闭新机制后是否符合预期的对照；不要求不适用的方法强行退化。
3. 检查张量/标签语义、梯度、指标与小样本前后向。小规模检查（smoke）仅说明代码路径可执行，不是完整效果验证。
4. 按计划运行候选及必要对照。先做能证伪机制的最小实验；不通过时报告并重审假设，不自动扩为全量实验矩阵。

整个基线组合保留作最终比较。最小试验不必重跑全部方法，但必须使用有效对照，声明比较覆盖有限；若要主张优于组合中的方法，需要相容协议的实际结果。协议改变时重跑受影响的对照。

## 运行证据与边界

- 使用现有授权环境；新增付费资源、超预算、长任务范围不明时先交用户决定。
- 按 [research-records.md](research-records.md) 记录每次 smoke、调参、完整运行和失败；分别记录运行用途与重试关系。
- 保留命令、配置、代码/数据版本、环境、选择规则、资源与真实指标产物；可行时从预测复算指标。
- 等实际运行结束、检查产物后再判定结果。进程退出成功、日志目录存在或 checkpoint 写出均不等于性能有效。
- 基础设施失败先按已有规则修复/重试；不偷偷换标签、切分、目标或删掉失败。观察结果与解释分开写。
- 所有隐私、合法访问、许可证及发布限制随数据/模型保留；不能为了记录或展示而上传敏感样本。

## 分析与反馈

先对照方案的判别预测和竞争解释，再看 headline 指标。机制消融若同时改变计算、数据或参数量，不能把增益单独归因于机制。报告重复波动、负结果和缺失比较，不挑最好 seed。

| 实际结果 | 更新什么 | 回到哪里 |
|---|---|---|
| 技术故障/协议不兼容 | 运行失败、具体原因、修复范围 | 当前执行或 baseline 核验；不宣布假设失败 |
| 最小实验反驳机制 | 候选主张、反证及作者选择 | 创新质询 B，缩小、修改或放弃 |
| 指标涨但竞争解释未排除 | 暂时有效与机制未知分列 | 实验设计，补匹配对照 |
| 多方法共同残余失败 | 开发集失败地图及混杂检查 | 创新质询 A |
| 初步支持且比较有限 | 已支持的窄主张、缺少的强对照 | 在预算内补证；更大范围由用户决定 |

本轮结束更新方向日志和实验日志，用真实证据提出下一步。只有待回答的问题时一问后等待；不能代用户选择方向并无限训练。开发集生成的假设用未参与选择的证据确认，没有独立数据就保留探索结论。
