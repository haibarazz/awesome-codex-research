# CDS Baseline and Benchmark

建立后续创新可以依赖的方法比较。默认运行 **5–10 个常见 baseline＋约 3 个近期方法**；简单方法和项目现有方法包含在常见组内，重复方法只计一次。默认总规模约 8–13 个独立方法，数量不是研究质量证据。

本阶段需要：任务、数据/代码位置和可用资源；已有研究方向、Benchmark 或实验日志时接续使用。开始选方法与运行前读取 [benchmark-protocol.md](benchmark-protocol.md)；准备交付时读取 [benchmark-records.md](benchmark-records.md)。

## 1. 建立运行前协议

从现有数据、代码和结果确认任务、输入输出、标签含义与现实资源。先记录 `BENCHMARK_CONTRACT.md`：划分、泄漏边界、指标、调参/选模型规则、预算、重复运行及异常处理。

训练/开发集服务方法选择、失败诊断和创新迭代；最终测试集保留给独立确认。把已经查看过的结果记录下来。既有测试结果可以报告，但一旦据此选方向或改模型，不再称该集合为未使用的确认集。

## 2. 搜索并核验方法组合

按任务常见方法家族找 5–10 个代表性 baseline，再找约 3 个与任务/瓶颈相关的近期方法。使用当前官方论文、会议记录和作者仓库核验，写明检索日期和年份窗口；预印本与正式接收稿明确区分。

每个方法形成简短方法卡：来源/版本、纳入理由、核心机制、目标函数、信息流、关键假设、代码入口、适用条件、迁移改动和复现命令。机制结论须有正文公式/算法/段落或代码位置，不能用摘要补齐。

区分原数据上的复现、目标数据上的忠实迁移、必要接口适配及主动方法修改。改变监督语义、目标或信息流时标为新候选，不能计作源方法的忠实 baseline。

源码需先检查再在适当环境运行。无法取得代码时可依充分方法说明实现，但披露实现来源和未知；无法忠实实现则记录缺席理由。

## 3. 实际运行与比较

先核对用户委托是否包含执行，以及方法范围、资源上限和运行规模是否足够明确。只有查找/设计请求时不训练；未明确的重要成本、付费资源或范围扩张先交研究者决定。已有明确执行委托和预算时按其运行，不重复要求批准或另建授权状态。

先做数据、指标、前后向和 checkpoint 的小规模检查，再按统一协议运行全部选定方法。smoke 成功不计作完整 baseline 结果。

记录每次调参、seed、重试与失败；模型选择只依据开发集。保存配置、命令、代码/数据版本、环境、指标、预测或合法可保存的度量输入、训练日志和资源成本。

检查数值异常、数据泄漏和评测实现。与论文分数比较前先检查数据和协议是否一致；目标数据不同则公开分数不是预期必须达到的值。技术失败与方法无效分别记录。

在当前资源内执行可行的比较。若全部方法超出授权资源，明确缺少哪些运行、成本和可选缩减方案，不能擅自扩预算或用论文分数补齐。部分完成可交付，但写清选中、完整运行、可比和失败的方法数。

## 4. 形成创新依据

从已保存指标生成结果矩阵，只在兼容协议组内排名。记录最佳分数的不确定性、成本和缺失比较。

按开发集结果、稳定性、可修改性和成本选择日常迭代主 baseline；保留近期强方法的独立比较地位。主 baseline 未必最高分，选择理由写清。

在开发集上比较共同失败、方法间差异和近期方法的残余不足。每个失败切片带样本量、定义、结果位置、竞争解释和待检验原因。多个方法共同失败也可能来自标签/数据/评价问题，不能直接宣布模型创新机会。

运行后保存 `BASELINE_SNAPSHOT.md`，说明当前结果与缺口；后续协议变化另存版本，并重跑受影响对照。

## 5. 写入记录并交付

交付 Benchmark Contract、每个方法的卡/配置、实际结果矩阵、可比性说明、Baseline Snapshot 和失败地图；后两项可合并在一份人可读报告。详细布局见记录参考。

完整工作流中，每个真实运行自动写实验日志，baseline 选择及偏离计划理由写方向日志。使用本包 [research-records.md](research-records.md) 中的脚本记录；既有非标准日志按原格式接续，不另建平行事实源。

下一步用结果做改进机会诊断和候选质询。报告运行与证据缺口，不把“已准备命令”或“文件存在”写成复现完成。
